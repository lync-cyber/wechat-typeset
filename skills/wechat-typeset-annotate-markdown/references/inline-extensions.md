# 行内扩展判定规则（独家 reference）

> 5 种行内扩展的语义边界、密度规则、组合规则。供 annotator 在标注阶段判断"这个词该用哪种行内标记"。

## 总览

| 语法 | 视觉 | 语义 |
| --- | --- | --- |
| `==高亮==` | 荧光笔背景色 | 关键词强调（视觉醒目优先） |
| `[.着重.]` | 字下圆点 | 中文传统着重（语义优先，视觉克制） |
| `[~波浪~]` | 波浪下划线 | 警示性强调 / 疑问性 |
| `~~删除~~` | 删除线 | 原值已弃 / 修改痕迹 |
| `++插入++` | 下划线 | 新增 / 强调"加入"动作 |

## 各扩展用法

### `==高亮==` · 荧光笔

**用途**：用户视线扫读时不可错过的关键词。

**判定**：

- 关键词是文中的**新概念** / **核心论点的判定词** / **专有名词首次出现**
- 不是"形容词强调"（"特别好"的"特别"——别标）
- 不超过 3-5 个连续字符（标整句话视觉爆炸）

**例子**：

```markdown
RSA 算法的安全性建立在 ==大数分解的困难性== 上。
量子计算时代，Shor 算法把这个问题降到了 ==多项式时间==。
```

---

### `[.着重.]` · 中文着重号

**用途**：在中文段落中**语义级**的强调，视觉上比 `==` 克制。

**判定**：

- 强调"读者在心里多停留一拍"，不是"视线醒目"
- 适合学术 / 散文 / 严肃文体
- 特别适合短语（2-6 字）

**例子**：

```markdown
真正的工程艺术，是把 [.复杂留给系统、把简单留给用户.]。
```

**用 `==` 还是 `[.着重.]`**：

- 教程 / 营销稿 / 标题党风 → `==`
- 严肃媒体 / 学术 / 散文 → `[.着重.]`
- 同一篇文章里**不要混用**（视觉杂乱）

---

### `[~波浪~]` · 警示性强调

**用途**：表达"读者请注意"、"这点有疑问"、"未必"。

**判定**：

- 警示色彩比 `==` 弱、比 `[.着重.]` 强
- 经常用于"反直觉"、"陷阱"、"不确定"
- 中文用得不多，使用频率明显低于前两者

**例子**：

```markdown
工程实践中，[~异步并不一定更快~]——任务规模小时同步反而更快。
```

---

### `~~删除~~` · 删除线

**用途**：明示"原值已废"、"修改痕迹"、"幽默自嘲"。

**判定**：

- 不是写作克制——是想让读者看到"我改过"
- 营销稿常见（价格对比"~~原价 ¥99~~ 现价 ¥49"）
- 工程文档不常用，除非要展示"曾经我们这样做，现在改了"

**例子**：

```markdown
本文初稿写于 ~~周末闲暇~~ 连续三晚的崩溃修复过程中。
```

---

### `++插入++` · 下划线 ins

**用途**：与 `~~~~` 配对，表达"新增"。

**判定**：

- 几乎总是与 `~~删除~~` 一起出现
- 用在"diff 风格"展示中（"旧的废了，++新的来了++"）
- 单独使用时和 `==` 视觉相近，**优先用 `==`**

**例子**：

```markdown
新版协议把 ~~明文 token~~ 改成 ++ JWE 加密 token++。
```

---

## 密度规则

**全篇每千字 ≤3 处任意类型的行内扩展**。

- 一篇 2000 字文章：≤6 处
- 同一段落不超过 1 处（同段两个高亮 → 等于没高亮）
- 整段全标 → 等于没标，**移除全部，留出"密度感"**

**例子（红灯）**：

```markdown
==RSA 算法== 的 ==安全性== 建立在 ==大数分解的困难性== 上。
```

3 个高亮在 18 字内，读者大脑直接溢出。改为：

```markdown
RSA 算法的安全性建立在 ==大数分解的困难性== 上。
```

只标核心论点。

## 组合规则

行内扩展可以与标准 Markdown 强调组合：

```markdown
**==重点中的重点==**           // 粗体 + 高亮（可用，但密度严控）
*==倾斜的高亮==*               // 斜体 + 高亮（少用，视觉混乱）
[.关键.]点 + `代码`            // 着重 + 行内代码（OK）
~~原值~~ → ++新值++           // 删除 + 插入对照（OK）
```

**不要这样组合**：

- `**[.重复.]**` —— 粗体已是视觉强调，叠 [.着重.] 多余
- `==[~混合~]==` —— 两种背景级标记叠加，公众号渲染不稳

## 不同 persona 的偏好

| Persona | 偏好行内扩展 |
| --- | --- |
| `default` / `tech-explainer` | `==高亮==`（醒目教程风） |
| `tech-geek` | 几乎不用——工程文章靠 `` `code` `` 已够 |
| `business-finance` / `academic-frontier` | `[.着重.]`（学术克制） |
| `industry-observer` | `==高亮==` + `[.着重.]` 各占其位 |
| `literary-humanism` / `people-story` | `[.着重.]` 为主，`==` 少用 |
| `life-aesthetic` | 都少用——气质偏散文 |

不是硬规则，但偏好不一致会让作者风格"撞气质"。

## 不要做的事

- **不要用 `**==X==**`**——粗体 + 高亮叠加在公众号上视觉过载
- **不要给整段套行内扩展**——行内是"点"，不是"面"，面级强调用 `::: highlight`
- **不要在 `::: free` 之外用 HTML 行内标签**（如 `<u>` / `<mark>`）——契约外的 inline 在 wxPatch 层不保
- **不要在标题行（H1-H6）使用行内扩展**——标题本身已是视觉强调
- **不要在 `:::` 容器的 open 行（title 段）使用行内扩展**——`::: tip ==重要==` 会把 `==` 当字面量传给 renderer
